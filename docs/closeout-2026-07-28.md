## 1. Every check has a fixture, and every fixture was watched failing

The claim under test is the one a postmortem made and could not support: *every
check ships with a negative fixture that makes it fail.* At `c2ff9a0` that was
false — eight fixtures covered two of the three scripts, `lint-cadence` had
none, and `check-template.mjs`'s emit-grep would have rejected a cadence fixture
as guarding a code "no script emits."

```
$ node scripts/check-template.mjs
```
```json
{
  "ok": true,
  "required": 25,
  "minimal": {
    "validate":       { "ok": true, "claims": 2, "files": 2,
                        "byClass": { "product-code": 1, "external-primary": 1 } },
    "lint-structure": { "ok": true, "pages": 9, "errors": [], "warnings": [] }
  }
}
```

Exit 0, 18 fixtures, all three scripts covered. `examples/minimal` still passes
both checks, still pins a claim, still pins no `own-corpus` source, and now
carries an L2 decision bound to claims — without that last one the binding check
would be exercised only negatively, which is the same defect one level up.

### What this does not establish

`--refetch` is opt-in. A confabulated URL still validates green on a default
`validate` run; only the refetch pass resolves it. The fixture proves the check
works when asked, not that anyone asks. That gap is real and is not closed by
anything in this file.

## 2. Dogfooding the rules on our own packet

The second stop condition: take a packet built under the *old* method and replay
it under the hardened rules, rather than asserting the rules would have caught
it. The subject is an asset-ingress packet from the origin corpus whose `raw/`
holds excerpts of our own prior research, with four claims pinned at **L2**.

Five steps, each the previous one's error corrected. Every run is
`LLM_WIKI_ROOT` pointed at the packet.

**1 — as shipped.** Four L2 claims, no registry.
```json
{ "ok": false, "claims": 4, "errors": [
  "E_PROV_NO_REGISTRY raw/provenance.json is missing",
  "E_PROV_UNREGISTERED CLAIM-pkt-split.json … source src-programme-excerpt is not in raw/provenance.json …",
  "E_PROV_UNREGISTERED CLAIM-pkt-lifecycle.json … source src-lifecycle-excerpt …",
  "E_PROV_UNREGISTERED CLAIM-pkt-history.json …",
  "E_PROV_UNREGISTERED CLAIM-pkt-identity.json …" ] }
```

**2 — register the two sources truthfully** as `own-corpus` / `origin.type: own-project`.
```json
{ "ok": false, "claims": 4, "errors": [
  "E_PROV_LEVEL_CAP CLAIM-pkt-split.json … source src-programme-excerpt is own-corpus, which caps at L1 — state this as prose with a wiki link, not a pinned claim",
  "E_PROV_LEVEL_CAP CLAIM-pkt-lifecycle.json … src-lifecycle-excerpt is own-corpus …",
  "E_PROV_LEVEL_CAP CLAIM-pkt-history.json …",
  "E_PROV_LEVEL_CAP CLAIM-pkt-identity.json …" ] }
```
Honest registration is what fails it. No adversary, no mislabelling — the class
that describes the bytes accurately is the class that caps at L1.

**3 — drop the claims to L1, run `lint-structure`.** The decision page states its
evidence level in body prose, the way the old method did.
```json
{ "ok": false, "pages": 12, "errors": [
  "E_DECISION_NO_LEVEL decisions/asset-ingress.md: decisions need frontmatter `evidence: L0|L1|L2|L3` — a body-prose \"Evidence level\" line is a claim about the work, not a declaration a check can read" ] }
```

**4 — declare `evidence: L2` in frontmatter and bind all four claims.** The
binding is now real, which is precisely what makes it refusable.
```json
{ "ok": false, "pages": 12, "errors": [
  "E_DECISION_NO_EXTERNAL decisions/asset-ingress.md: evidence L2 needs at least one bound claim on an external-primary or external-secondary source; bound classes are CLAIM-pkt-lifecycle=own-corpus, CLAIM-pkt-identity=own-corpus, CLAIM-pkt-split=own-corpus, CLAIM-pkt-history=own-corpus" ] }
```

**5 — declare `evidence: L1`.**
```json
{ "ok": true, "pages": 12, "errors": [], "warnings": [
  "registered source src-lifecycle-excerpt has no page under wiki/sources/",
  "registered source src-programme-excerpt has no page under wiki/sources/" ] }
```

**The packet lints clean at L1 and at no level above it.** Which is the correct
answer: the work is sound, the reasoning is ours, and nothing outside our own
output was ever consulted. L1 is not a demotion, it is the accurate label. What
the old method produced was the same packet wearing L2, and nothing anywhere
could tell the difference.

The two remaining warnings are honest too — registered sources with no page
under `wiki/sources/`. Warnings, not errors, because an unwritten source page is
incomplete work rather than a false claim.

## 4. The cadence check aimed at the corpus that motivated it

`lint-cadence` was written in response to a specific closeout day and, as
shipped, could not be pointed at it — `wiki/decisions` was hardcoded. With
`--dir`, against that history (read-only, `git log` only), scoped to the range
that day spans:

```
$ LLM_WIKI_ROOT=…/<origin-repo> \
    node template/scripts/lint-cadence.mjs \
      --dir .claude/research/<corpus> \
      --since 2026-07-27T01:35:53-03:00
```
```json
{
  "ok": false,
  "watched": [".claude/research/<corpus>"],
  "closes": 251,
  "days": { "authored": 1, "committed": 1 },
  "medianGapMinutes": { "authored": 0, "committed": 0 },
  "busiestDay": { "authored": ["2026-07-28", 251], "committed": ["2026-07-28", 251] }
}
```

299 violations: 55 `E_CADENCE_BATCH`, 1 `E_CADENCE_DAY`, 243 `E_CADENCE_GAP`.

```
E_CADENCE_BATCH c218a831b: 63 closes in one commit (limit 1)
E_CADENCE_BATCH 6c6121b28: 21 closes in one commit (limit 1)
E_CADENCE_BATCH 8a6e6c596: 12 closes in one commit (limit 1)
E_CADENCE_DAY 2026-07-28: 251 closes (limit 6)
E_CADENCE_GAP …/prototypes/<page>/README.md: 0.0 min after the previous close (limit 15)
```

The `--since` bound is the commit date of the range's first commit; there are
zero adds under that directory after the range's last commit, so this is the
range exactly. Widen it to all history and the same command reports 407 closes
over five days and 474 violations — recorded, with the `c2ff9a0` comparison, in
[`examples/failing/cadence-batch/regression-2026-07-28.md`](examples/failing/cadence-batch/regression-2026-07-28.md).

251 closes in one day at a median gap of 0.0 minutes. The limits are defaults,
not a verdict; an instance picks its own numbers in `cadence.json`. What is not
negotiable is that a number exists and something checks it.

### And what cadence still cannot do

Both timestamps git records are environment variables. Six closes committed
seconds apart, with `GIT_AUTHOR_DATE` and `GIT_COMMITTER_DATE` forged across two
days, pass: `{ok: true, medianGapMinutes: 60, violations: []}`. Reading both
dates raises the cost of forgery, it does not remove it. The earlier docstring
called cadence "the one signal the thing being measured cannot author"; that was
false, it has been corrected in the source, and no prose in this repo makes the
claim any more. The honest framing is a signal an agent is unlikely to think to
author — which is worth having, and is not a guarantee.

## Correction — the dogfood replay's endpoint (same day, second session)

Section 2's step 5 recorded the packet "linting clean at L1" with the four
claims still on disk at `level: L1`. That state passes `lint-structure` and
**fails `validate`**: pinned claims must be L2 or L3 (`E_LEVEL`), which this
file did not run against the final state. The honest final form is `claims/`
**empty** — the four statements become prose with wiki links, exactly what
`E_PROV_LEVEL_CAP`'s message instructs — with the decision at `evidence: L1`:
`validate` ok (`claims: 0`), `lint-structure` ok (`pages: 12`).

The replay behind this correction ran against the packet copied byte-identical
(sha256 verified per file) from the private dogfood snapshot, using this repo's
scripts at `c5416a0`. The correction strengthens the
conclusion: the claims layer does not cap this packet at L1 — it ejects it.
Nothing the packet pinned was ever a claim about anything outside our own
output.
